## Destination

An implementation-ready spec for a personal Antigravity extension (VS Code only if that comes almost free) that shows, view only, a **Token Gauge** in the status bar and a **Context Inventory** sidebar tree for the **Active Conversation** plus up to 2 **Recent Conversations** (see [GLOSSARY.md](../../GLOSSARY.md)). Feasibility proven, data sources chosen, UI and architecture decided, ready to hand to a build session.

## Notes

- Domain: VS Code extension API, Antigravity internals (brain folders, transcript files, the `state.vscdb` database), WSL2 with a Windows host.
- Settled while charting: jobs are watching the budget and debugging the agent, view only (no editing the context). Live updates (a few seconds of lag is fine) plus a refresh button; change detection is stat polling everywhere (see the architecture decision). Status bar gauge, e.g. `ctx 62% · 124k/200k`; clicking it opens the sidebar tree grouped by kind of item. Gauge used = latest step's `input_tokens + cache_read_tokens`; running totals go in the tooltip. Per-item counts are estimated from the text and marked `~est`. May read undocumented internal state, read only, accepting breakage on Antigravity updates; no patching or injection. Model limits: see the context-limit decision. Brain roots are an editable settings list (default `~/.gemini/antigravity/` only; see the data-source decision). Recent Conversations: cap 2, dropped after 3 minutes, both adjustable. Label = the real title if one can be found, otherwise the first prompt cut to ~40 characters plus last-activity time. TypeScript, esbuild, standard extension scaffold. Personal use, installed from a local package file.
- Every grilling session: call the `grilling` and `domain-modeling` skills; keep [GLOSSARY.md](../../GLOSSARY.md) current.
- Tracker: local markdown (this folder). Claim a ticket = set `assignee:`. Blocking = `blocked_by:` in the frontmatter. Research findings go in `docs/research/` (not a git repo, so no `research/` branches).

## Decisions so far

- [Where does the extension run under WSL, and what can it reach?](04-extension-host-wsl.md): `extensionKind ["workspace","ui"]`, both sides can reach every root; inotify misses changes on /mnt/c, so poll there (1-2s on the active transcript, 5-10s directory scan) and watch natively elsewhere; no Antigravity API exposes conversation state.
- [What does state.vscdb hold for Conversations (titles, timestamps, model)?](02-state-db-index.md): only a stale protobuf index (`trajectorySummaries`: ids, titles, timestamps, no model). The wrong source; the live data is in `.gemini/antigravity/` (`conversation_summaries.db`, `conversations/<id>.db`, `antigravity_stats_cache.json`). Possible selection lead: the `antigravity-multi-conversation-layout-v3-<uuid>` keys.
- [Can the extension detect which Conversation is selected?](01-selection-signal.md): yes, from files only. Use the newest `last_user_view_time` across `~/.gemini/antigravity/annotations/<uuid>.pbtxt` (no lag; the file also holds the real title), cross-checked with the per-window `lastConversationId` (workspace state.vscdb, ~19s lag), then fall back to the newest transcript write. `antigravity_state.pbtxt` holds `last_selected_agent_model`.
- [What do transcripts contain, and how do they map to Context Items?](03-transcript-format.md): read the append-only `transcript_full.jsonl`; take the last kept step, since `step_index` going backwards marks a rewind. Gauge = `input_tokens + cache_read_tokens`, counted on planner steps only, with an n/a state for old Conversations. The system prompt, rules, knowledge and memories are NOT in the transcript; they appear only as an unattributed baseline of 4k–16k tokens. Visible: user requests, attached metadata (open files, skills), system messages, tool calls and results. Model names appear only as occasional `Model Selection` deltas, and limits must be built in. About 3 characters per token.
- [Do the installed context-monitor extensions already meet the destination?](12-prior-art.md): no. Build from scratch and take ideas. `n2ns.antigravity-panel` (Apache-2.0) shows one Conversation in a webview, with no gauge and no inventory. Key idea: it queries the language server's Connect-RPC (`GetCascadeTrajectoryGeneratorMetadata` returns `maxContextTokens`, `estimatedTokensUsed`, `truncationReason`), and it has solid WSL path handling. Downside: finding the language-server process is fragile (open `no_process` bugs).
- [Which .gemini data store is the best source for titles, model and tokens?](09-gemini-data-stores.md): Conversation list and titles from `conversation_summaries.db` (live; fall back to `preview`, then the first prompt). Model, tokens and limit from the latest `gen_metadata` row in `conversations/<id>.db`: the display name, a context limit (e.g. 256000), and an exact System Prompt / Tools / Chat Messages breakdown. Ignore the stats cache. Only `~/.gemini/antigravity/` on the WSL side is live. To read safely, copy the db, `-wal` and `-shm` together.
- [Which brain root and data folder does the current IDE write to?](08-active-brain-root.md): answered by the data-store research: `~/.gemini/antigravity/` (WSL) is live; the Windows-side and `antigravity-ide` roots are stale or left over.
- [What can the language server's RPC tell us, and can we reach it reliably?](13-language-server-rpc.md): yes, for WSL windows. Each window has its own `~/.gemini/bin/agy`; the port and CSRF token come from `/proc/<pid>/cmdline`; Connect-RPC JSON over the loopback hub port; ~30 ms per call and live. `GetCascadeTrajectoryGeneratorMetadata` returns `maxContextTokens`, `estimatedTokensUsed`, the model, and a breakdown (System Prompt sections incl. `user_rules` and `skills`, per-tool counts, per-step messages); `GetTokenBase` itemizes each rule and skill. The token also allows write methods, so the extension needs a hard Get/List allowlist and must never log the token. Windows-window discovery and compaction (`truncationReason`) remain unverified.
- [Files only, or language-server RPC with files as fallback?](14-data-source-strategy.md): the language server (this window's own) is the main source, with a hard Get/List allowlist, called only when files change; the files are the fallback, and the gauge is marked `rpc`/`file`. Only default root: `~/.gemini/antigravity/`. Gauge = billed input + cached from either source; Antigravity's estimate goes in the tooltip (not a fixed offset: higher when small, up to 25% lower when large; see the compaction decision).
- [Which kinds of Context Item does the inventory show, and how are they grouped?](05-context-item-taxonomy.md): System Prompt / Tools / Chat Messages groups with exact server counts; Chat Messages in time order, items over 5% of the window highlighted, a largest-first toggle, kind shown as an icon; tool call and result merged into one item (`#42 view_file src/foo.ts · 3.1k`); per-rule and per-skill children only if they add up; "loaded" = the latest server breakdown; file fallback is the same tree, `~est` with a Baseline remainder.
- [Does switching Conversations update the selection signals as expected?](10-selection-click-test.md): the window's `lastConversationId` is the reliable selection signal (~0.1-1s; cleared on a new chat). The annotation view time ties the old and new Conversation on every switch, so it means "last seen" and suits the Recent list only. Retry broken `state.vscdb` copies. Transcript and db update together. 10 of 12 language servers are orphans to skip.
- [With several windows open, which Conversation is Active?](11-multi-window-active.md): per window, from its own `lastConversationId`. When nothing is selected, keep the last one, dimmed and marked "not selected". Recent Conversations come from any workspace, ranked by the later of last seen and last written. Ask this window's own server, falling back to files per Conversation.
- [How is the model's context limit worked out when no source gives it?](06-model-limits.md): remember every limit seen, keyed by model name without the effort level; built-in table only for confirmed values (Gemini 3.8 Flash and Gemini 4 Argon, both 256000). Source order: override > server > database > remembered > built-in > default (empty). With no limit, show `124k / ?`. After a model switch, keep the last call's limit until the next turn.
- [How should the status bar gauge and sidebar tree look and behave?](07-ui-prototype.md): variant A: one tree with each Conversation as a root, Active first; `maxConversations` (default 3) caps the tree and the status bar; with Recent ones, one status bar item per Conversation with a short title. Colour = used ÷ Threshold (per model, else default 150k; entered in thousands): ≤50% green text, >50% yellow text, >80% amber, >100% red background.
- [How do the data sources, watching, parsing and UI fit together?](15-architecture.md): modules feed one store that the views subscribe to, and colour is computed when the views render; one stat poller (1-1.5 s on tracked files, 5 s scans, 5× slower when the window isn't focused) instead of `fs.watch`; pull server metadata on change (wait 500 ms, one call in flight), keep only the latest breakdown, back off if slow; file mode reads only new transcript lines plus `node:sqlite` on a copy opened read-write; only the remembered limits persist; expiry removes the tree root and the status bar item together; empty state, logging with redaction, vitest on the pure functions.
- [What do the gauge and inventory show when Antigravity compacts or drops earlier context?](16-compaction.md): compaction (manual `/compact` or automatic at ~the 256k limit) writes a `CHECKPOINT` step and the next call carries `startStepIndex` + `truncationReason`; the gauge just shows the new figure and can pass 100%; the tooltip shows `Compacted N× (M manual) · was X`, `Compacts at ~256k`, and model changes (the `cd5f84af` drop was a model switch); the tree starts at a `Compaction summary` item; stale-server guard added to the architecture.
- [How much raw content does a hover show, and does it ever show tokens or account details?](17-hover-content.md): head 1,500 + tail 500 characters (`contextViewer.hoverChars`, default 2000), thinking gets its own 1,000; non-chat items show metadata only (no System Prompt text, so no `user_information`); only the live CSRF token is masked (`‹csrf›`); untrusted MarkdownString; text read lazily from the transcript on hover.
- [What shape does the handoff spec take, and what goes in it?](18-spec-assembly.md): one self-contained `docs/spec/context-viewer.md` (≤ ~700 lines, `Why:` links to tickets) in 15 sections ordered by module, with Safety, Build-time checks, Later (push, Windows-local server data, plain VS Code) and 8 suggested vertical slices; 2 ADRs (RPC-primary, stat polling); commit the trail after a redaction check; the build session files the slices as GitHub `ready-for-agent` issues. Writing goes to [Assemble the handoff spec](19-assemble-spec.md).
- [Assemble the handoff spec](19-assemble-spec.md): written. [The spec](../../docs/spec/context-viewer.md) plus ADRs [0001](../../docs/adr/0001-rpc-primary-source.md) and [0002](../../docs/adr/0002-stat-polling.md), committed with the trail. ## Out of scope

- Curating context (add/remove items): view only, by decision.
- A full transcript viewer.
- Publishing to Open VSX.
- Push updates (`StreamCascadeReactiveUpdates` instead of pulling on change): beyond v1, by the architecture decision; recorded under "Later" in the spec.
- Server data from Windows-local windows (finding the server without `/proc`): beyond v1, which uses files only there; recorded under "Later" in the spec.

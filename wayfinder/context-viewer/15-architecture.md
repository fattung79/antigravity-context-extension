## Question

Decide the module layout and data pipeline: a source per Conversation (language server, falling back to files), what triggers a re-read (native watcher vs polling on /mnt/c, the selection signal, the refresh button), polling `GetCascadeTrajectoryGeneratorMetadata` on file change vs `StreamCascadeReactiveUpdates` push, payloads that grow ~6 KB per call with no pagination, caching, and how the tree, the status bar items and the threshold colouring subscribe to one model. Inputs: the decisions on the extension host, data sources, multi-window selection and the UI prototype.

## Resolution

- **Modules:** `config`, `discovery` (roots, Conversation list, selection, Recent ranking and expiry), `sources/rpc` (server lookup, Get/List allowlist, reply → snapshot), `sources/file` (transcript + `conversations/<id>.db` → the same snapshot type), `limits` (remembered limits), `model` (one store of snapshots per tracked Conversation, emits changes), `ui/statusBar`, `ui/tree`, `ui/decorations`. Views subscribe to `model` only and never touch a source. Snapshots hold raw facts (used, limit, model key, source, groups, totals); a pure `classify(used, threshold)` in `ui/` derives colour when the views render, so settings changes only redraw.
- **Change detection: one stat poller (mtime + size), no `fs.watch`.** Tracked Conversations' transcript and `conversations/<id>.db` every 1.5 s; this window's `state.vscdb` (selection) every 1 s; `annotations/` listing + `conversation_summaries.db` every 5 s. An unfocused window polls 5× slower (7.5 s / 25 s) and catches up at once on focus. Replaces the earlier "watch natively elsewhere".
- **Server data: pull on change.** When a tracked file changes, wait 500 ms for activity to settle, then call `GetCascadeTrajectoryGeneratorMetadata`; at most one call in flight per Conversation, plus one follow-up call if a change arrived during it. Keep only the latest breakdown + running totals and discard the rest of the reply (it has no pagination and grows ~6 KB per call). Log reply size and fetch time at debug level. If a reply takes over 2 s, back off to one call every 10 s for that Conversation. `StreamCascadeReactiveUpdates` (push) deferred.
- **Server lookup and recovery:** find this window's server through `/proc` (the extension host is its parent process) when the extension starts. On a connection failure or a 401/403, switch every Conversation to `file` at once, then retry the lookup after 5 s, 15 s, 30 s, then every 60 s; success switches back to `rpc`. Token held in memory only. Windows-local (non-WSL) windows: files only in v1, read over `\\wsl$`.
- **File mode:** the transcript is read only from where the last read stopped (one byte position per file); it is read from the top again if the file shrinks, and held later steps are dropped when `step_index` goes backwards. SQLite: built-in `node:sqlite` (Antigravity's extension host is Node v22.21.1 with SQLite 3.50.4; it loads without flags but logs an ExperimentalWarning). Copy the `.db`, `-wal` and `-shm` together into the extension's storage folder, open the **copy read-write** so SQLite merges the WAL into it, never open the originals, and read again only when the source's mtime or size changes. If `node:sqlite` is missing, file mode uses the transcript only (no model, limit or breakdown). The build session confirms once, with a non-empty WAL, that this merge works.
- **What persists:** only the remembered model limits are saved (`globalState`). Snapshots, the Recent list and timers live in memory only and rebuild within one poll. Refresh = find the server again + ignore the "only when a file changed" check + read every tracked Conversation again from its best source; it doesn't reset the expiry timers.
- **Recent Conversations:** every 5 s, read each Conversation's "last seen" time from the `annotations/` files whose modification time changed, plus "last written" times and titles from `conversation_summaries.db`. Rank by the later of the two, take the top `maxConversations` − 1, leaving out the Active one. Each Conversation's 3-minute timer lives in the store; expiry removes both its tree root and its status bar item. The countdown shows minutes only (`drops in 3m`, then `<1m`) and redraws every 15 s; in the status bar it appears only in the tooltip. When the last Recent Conversation drops, the status bar goes back to the single Active item with its full label. A Conversation that becomes active again takes the Active slot and its timer is cancelled.
- **Empty state:** status bar `◌ ctx —` with the tooltip "No Conversation yet"; the tree shows a welcome message "Open or start a Conversation in the agent panel." with a Refresh link; if the roots don't exist, the welcome message says so and links to the `roots` setting.
- **When it starts and how it reacts:** start on `onStartupFinished`. Settings changes: threshold/colour settings → redraw only; `roots` → scan the Conversations again; `maxConversations` → rank the Recent list again; `logLevel` → apply straight away. Unloading the extension stops every poller and timer.
- **Logging:** output channel "Context Viewer", `contextViewer.logLevel` (off/error/info/debug, default error); logs source switches, failed server lookups, db copy/open failures, and reply size and fetch time at debug level. A redaction step drops anything that looks like the CSRF token or a `GetUserStatus` field.
- **Tests:** vitest on the pure functions (transcript parser, server reply → snapshot, `gen_metadata` → snapshot, `classify`, Recent ranking and expiry, model-limit lookup) using captured fixtures from `docs/research/`; injected clock and filesystem/process interfaces; no tests that drive the actual VS Code UI.

**Amendment** (from [the compaction decision](16-compaction.md)): stale-server guard. If this window's server's latest call trails the transcript's last planner step for 2 consecutive checks, treat it as stale: switch to files and look for the server again.
